# 核心代码阅读与答辩准备

## 先运行一条完整流程

使用虚构资料注册，搜索商品并加入购物袋。提交订单后观察库存变化，再演示付款、用管理员发货，查看测试邮箱中的邮件，最后由顾客确认收货。然后另建一笔未付款订单，取消后核对库存恢复。

## 应能解释的核心逻辑

1. `AuthController.signIn`：创建认证信息，替换Session ID并保存服务端认证上下文。密码原文只用于校验，数据库保存BCrypt哈希。
2. `SecurityConfiguration`：公开浏览接口与需要登录的接口分开，管理路径额外检查ADMIN角色，写请求保留CSRF校验。
3. `CartService`：购物袋按用户隔离，数量必须为1至99且不超过可售库存。购物袋中的库存检查不等于下单时已经预留库存。
4. `OrderService.checkout`：锁定同一顾客以避免并发清空同一购物袋；识别幂等键后，以条件更新扣减库存，最后在一个事务中写订单和快照。
5. `OrderService.pay`：只允许待付款状态进入已付款，付款记录的订单唯一约束防止重复记账。本项目是演示付款，没有接入资金结算。
6. `OrderService.cancel`与`expire`：只释放未付款订单的库存；已取消的重复请求不再次加库存，已付款订单不被超时任务取消。
7. `OrderService.ship`与`MailDispatcher`：发货和邮件任务一起落库，SMTP发送放在事务外。任务失败会延迟重试，崩溃中的过期任务可重新认领；极端情况下可能重复通知，不能声称严格只发送一次。

## 用测试证明判断

- 两人争抢最后一件商品：只能一人成功，库存不能变成负数。
- 多商品订单的后一件库存不足：前面已经扣减的库存也必须回滚。
- 重复下单或付款：相同业务请求不会形成第二条订单或付款记录。
- 普通顾客访问管理接口：被拒绝；读取他人订单不能得到对方的订单资料。
- 邮件重试和页面时间：检查失败后的延迟，以及UTC邮件时间转换为北京时间的回归测试。

## 商品资料与展示数据

原始名称和来源链接说明资料从哪里来；中文导读名帮助检索，不能据此声称是对应的中文出版版本。书封面为原创示意设计，价格和库存是演示值。32笔预置订单只用于展示，不是个人真实经营历史。
